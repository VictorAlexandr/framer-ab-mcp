The insight

The data was never locked — it was in GA4 all along

When Framer assigns a visitor to an A/B variant, it stamps ?framer_variant=<id> on the URL. If your site sends data to Google Analytics 4, every variant is already tracked separately — through an official, stable Google API. No scraping. Nothing to break.

Quickstart

Running in three steps

Connect GA4 to your Framer site

Site Settings → Integrations → Google Analytics. Most production sites already have this. Mark your lead/purchase event as a key event in GA4.

Create GA4 API credentials (2 min)

Google Cloud → enable the Analytics Data API → create a service account → add its email as Viewer on your GA4 property → download the JSON key.

Add the server to your MCP client

{
  "mcpServers": {
    "framer-ab": {
      "command": "npx",
      "args": ["-y", "framer-ab-mcp"],
      "env": {
        "GA4_PROPERTY_ID": "123456789",
        "GOOGLE_APPLICATION_CREDENTIALS": "/path/to/key.json"
      }
    }
  }
}

Honest FAQ

What it is — and isn't

Is this scraping Framer's dashboard?

No. It only calls the official Google Analytics Data API on data your own site sends to your own GA4 property. Nothing touches Framer's servers, so nothing breaks when Framer ships a redesign.

Does it cover Framer's native funnels and CTA click tracking?

No — those metrics exist only inside Framer's panel, which has no API. This project deliberately stays on the official-API side of that line. If Framer ever ships an analytics API, this server is the natural place to plug it in.

Which AI clients work?

Anything that speaks MCP over stdio: Claude Code, Claude Desktop, Cursor, Windsurf, and the growing list of MCP-compatible agents.

What about visitors from before the test started?

They land without a framer_variant stamp and are reported as (baseline) — kept separate so they never contaminate your variant numbers, and used as control by default.
